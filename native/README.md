# Marker One — native

Cross-platform native AR, on the free tier: **Unity + AR Foundation + ARCore
Extensions**, with the **ARCore Geospatial API** doing the localizing on both
Android and iOS.

The web app is not being replaced. It keeps the things it is good at — no
install, marker and poster tracking that work on any phone including iPhones,
and a link you can send someone. What it cannot do is put content at an
arbitrary coordinate accurately, because that needs an API no browser exposes.

## Why this shape

| | |
|---|---|
| **Urban** | Sub-metre position, ~1° heading wherever Street View reaches |
| **Rural** | Degrades to fused GNSS + visual-inertial odometry — several metres, but with a *real* heading estimate and an honest per-fix accuracy figure, which is already far better than a magnetometer |
| **iOS** | ARCore SDK for iOS runs the same Geospatial API on top of ARKit |
| **Cost** | Free runtime; Unity Personal free below the revenue threshold |

## What is here

```
MarkerOne.Core/          the portable half — no UnityEngine reference anywhere
  Types.cs               GeoPoint, Ecef, Enu, Vec3, Quat — all double precision
  Geodesy.cs             WGS84, ECEF, ENU, render frame, geohash, orientation
  LocalizationFrame.cs   global <-> session-local, the seam everything turns on
  Baseline.cs            heading from a walked baseline
MarkerOne.Conformance/   checks the port against the web implementation
vectors/core.json        generated by scripts/make-vectors.mjs — do not edit
```

`MarkerOne.Core` targets `netstandard2.1`, which is what Unity compiles
against, and references nothing. That is deliberate: the moment it depends on
`UnityEngine` it can only be tested inside an editor, and this is precisely the
part worth testing without one.

**Everything is `double`.** A `float` loses centimetres a few hundred metres
from the origin, which is the entire range this works in. Convert to
`Vector3` at the boundary, not before.

## Proving the port

The geodesy in `spatial/` has a hundred-odd assertions behind it and two
corrected sign errors in its history — a mirrored render frame and a quaternion
facing backwards. Neither announced itself as anything except the world being
subtly wrong, and one survived a round-trip test because a mirrored transform
is its own consistent inverse.

So the C# is not tested against its author's intentions. It is tested against
the same inputs and outputs, produced by code known to work:

```bash
node scripts/make-vectors.mjs                                  # regenerate
dotnet run --project native/MarkerOne.Conformance -- native/vectors/core.json
```

1411 vectors, all matching. Reintroducing either historical sign error fails
456 and 69 of them respectively — the check has been confirmed capable of
failing, which is the only reason to believe it when it passes.

CI regenerates the vectors and fails if they differ from what is committed, so
the two implementations cannot drift apart quietly.

## Setting up the Unity project

Not scaffolded here on purpose: Unity writes its own project layout, and a
half-made one is harder to work with than none. In the editor:

1. **Unity 6 LTS**, 3D (URP) template.
2. Package Manager → **AR Foundation**, **Google ARCore XR Plugin**,
   **Apple ARKit XR Plugin**.
3. **ARCore Extensions** — from the `arcore-unity-extensions` repository, added
   by git URL. This is what carries the Geospatial API.
4. Copy `MarkerOne.Core/*.cs` into `Assets/MarkerOne/Core/` with an assembly
   definition, or reference the built DLL. The conformance project stays
   outside Unity and keeps running under `dotnet`.
5. **Google Cloud**: enable the *ARCore API*, and use keyless authorization —
   the recommended route, and it avoids shipping a key in the binary.
6. Player settings: minimum **Android 7.0 / API 24**, **iOS 12**, and camera
   and location usage descriptions on both.

## What carries over from the web app

| Carries over | Does not |
|---|---|
| `content.json` — scenes, layers, targets | The DOM, A-Frame, AR.js |
| Firestore schema, rules, indexes | The service worker and offline shell |
| GeoPose records already written | WebXR hit-test and dom-overlay |
| The geodesy, now proven identical | Link-without-install distribution |
| `assets/*.glb` unchanged | |

Placements made by the web app are readable by the native app and the reverse,
because both speak the same global frame and the same documents. That was the
point of storing GeoPose rather than a local transform.
